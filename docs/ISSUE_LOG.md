# Issue Log

Annex document tracking technical issues encountered during setup and
execution, and how each was resolved. Not part of the core protocol
documentation (see README.md for the full required document list) —
this is supplementary evidence of methodical process.

| # | Phase | Issue | Root cause | Resolution |
|---|---|---|---|---|
| 1 | Repo setup | `python -m venv .venv` failed with `KeyboardInterrupt` | Process interrupted during `ensurepip` step (likely accidental Ctrl+C or antivirus scan delay mistaken for a hang) | Removed the partial `.venv` folder and re-ran the command without interrupting it |
| 2 | Repo setup | `.gitignore` contained literal PowerShell here-string syntax (`@"..."@`) instead of its intended content | Copy-pasting a multi-line PowerShell here-string block into an already-open interactive terminal does not execute it as a command | Deleted the file and recreated it directly in the VS Code editor instead of via terminal here-string |
| 3 | Repo setup | GitHub blocked merging the first PR with "Review required" despite solo development | Default branch protection rule ("Require a pull request before merging") auto-enabled "Require approvals," which cannot be satisfied by the PR author on their own PR | Disabled "Require approvals" in the branch protection rule; enabled "Require status checks to pass" (CI) instead, which fits solo development |
| 4 | Runtime selection | Branch protection rule showed "Not enforced" even after configuration | GitHub does not enforce branch protection rules on **private** repositories on the free plan | Changed repository visibility to public (also appropriate for a submission meant to be reusable by other developers) |
| 5 | Runtime selection | `pip`-installed `litert-lm` CLI has no way to target the connected Pixel 7 | The CLI installed via `pip` runs inference locally on the host machine only; Android execution requires a separately built, device-targeted binary | Switched to building `litert_lm_main` from source via Bazel with `--config=android_arm64`, using WSL2 + Android NDK r28b |
| 6 | Runtime deployment | `CANNOT LINK EXECUTABLE`: `libGemmaModelConstraintProvider.so` not found | The natively-built `litert_lm_main` binary depends on a shared library not produced by its own Bazel build target — it is a prebuilt dependency referenced via `//prebuilt/android_arm64:...` in the BUILD file, not compiled from source by the `litert_lm_main` build | Located the file in the cloned repo's `prebuilt/android_arm64/` directory, confirmed it was a real binary (not a Git LFS pointer), copied it alongside the main binary and pushed both to the device |
| 7 | Runtime deployment | `CANNOT LINK EXECUTABLE` persisted even after pushing the missing `.so` to the same device directory as the binary | Android's dynamic linker does not automatically search an executable's own directory for shared libraries on `/data/local/tmp/` | Explicitly set `LD_LIBRARY_PATH=/data/local/tmp` on every invocation of the binary via `adb shell` |
| 8 | Measurement testing | `--max_output_tokens` and `--max_num_tokens` had no measurable effect on generation length across 5 consecutive test runs with `litert_lm_main` — all produced exactly 920 output tokens regardless of flag value (250, 20, or unset) or which flag was used | Source verification (`grep` on `runtime/engine/litert_lm_main.cc`) confirmed this binary never reads `FLAGS_benchmark_prefill_tokens` or `FLAGS_benchmark_decode_tokens` — that logic exists only in `runtime/engine/litert_lm_advanced_main.cc`. The exact mechanism that stopped generation at 920 tokens in `litert_lm_main` (EOS token vs. an untested internal limit) was not further diagnosed, since the binary itself was the wrong tool for length-controlled measurement | Switching the primary measurement binary from `litert_lm_main` to `litert_lm_advanced_main`, which implements `settings.benchmark_prefill_tokens` / `settings.benchmark_decode_tokens` and the `--benchmark` mode required by the project's fixed workload constraints (§5) |
| 9 | Measurement testing | `litert_lm_advanced_main --benchmark=true --benchmark_prefill_tokens=15 --input_prompt=...` produced 0 prefill turns and 0 decode turns — no generation occurred | Source verification (`runtime/engine/litert_lm_lib.cc`) showed `benchmark_prefill_tokens > 0` activates a synthetic fake-prefill-token mode that discards the real input prompt and suppresses output printing (`should_print_output = benchmark_prefill_tokens == 0`) | Confirmed the working combination: `--benchmark=true` alone (without `--benchmark_prefill_tokens`/`--benchmark_decode_tokens`) combined with `--max_output_tokens` correctly limits real-prompt generation while still producing BenchmarkInfo metrics |
| 12 | Model/workload prompt design | Multiple prompt variants tested on the same source document produced inconsistent output formats/quality between runs, raising a question of whether variance came from prompt changes or from non-deterministic sampling | No `--seed`, `--temperature`, `--top_k`, or `--top_p` flags were found in `litert_lm_advanced_main`'s flag set (unlike the `pip`-installed CLI, which does expose these). The sampling strategy actually used by default (greedy/deterministic vs. probabilistic) could not be confirmed via a brief source investigation (`runtime/engine/litert_lm_lib.cc`, `shared_flags.cc`) | Investigation was stopped per §15 (do not spend V1 time exhaustively diagnosing a secondary point). Documented as an open uncertainty rather than resolved. Mitigation: prompt reliability will be assessed empirically through Phase A's existing 5-runs-per-document design, which already averages over multiple generations rather than relying on a single sample -- the same safeguard applies regardless of the underlying cause of variance |
| 13 | Model/workload prompt design | Confirmed the frozen prompt (arrow-schema format, ISSUE_LOG.md #11) against 4 structurally distinct alternatives (table format, SI/ALORS conditional format, two-section concepts+relations format, guided Q&A format), all tested on the same MESI source document with the same 400-token budget | Comparative evaluation across 6 criteria (French correctness, isolated EN terminology, structure adherence, fidelity/completeness, clean conclusion, token efficiency) | Arrow-schema format (Prompt A) was the only one to pass all 6 criteria simultaneously: table format embedded full English clauses in "concept" cells rather than isolated jargon; SI/ALORS and guided Q&A formats each dropped one source relationship; two-section format was complete but truncated mid-word at the 400-token limit. Confirms the frozen prompt is a robust choice, not a lucky single result |
| 14 | Model/workload prompt design | The frozen prompt (ISSUE_LOG.md #13) omitted the source document's general context (what/why), and a first attempt to fix this by asking for contextual synthesis caused the model to invent an unsupported relationship not present in the source text | Requesting synthesis/interpretation (even briefly) gave the model latitude to extrapolate beyond the source, risking a critical semantic error rather than a mere omission | Replaced the synthesis request with a bounded, literal instruction: translate the source's own opening sentence as-is, plus an explicit "do not infer or add" guard. Verified fidelity line-by-line against the source document — no omissions, no inventions. This is the final frozen prompt |
